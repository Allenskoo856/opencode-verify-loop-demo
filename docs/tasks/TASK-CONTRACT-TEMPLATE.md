>
> 来源：Jira/禅道/需求文档链接或编号
>
> 审核人：<产品负责人>、<技术负责人>、<测试负责人>

## 目标与边界

- 目标：用一句可验证的话描述用户价值。
- 本次包含：列出模块、接口、页面或迁移。
- 本次不包含：明确不做的能力，避免模型扩大范围。
- 风险：数据写入、权限、外部依赖、兼容性、回滚要求。

## 不可变验收条件

使用可观察的 Given/When/Then 或编号断言；每条必须能映射到 API、单测、集成测试或 E2E 之一。

1. Given <前置条件>，When <动作>，Then <可观察结果>。
2. Given <异常前置条件>，When <动作>，Then <错误码/错误信息/页面状态>。
3. Given <权限或边界条件>，When <动作>，Then <拒绝或审计结果>。

## 验证映射

| 验收条件 | 自动化层 | 对应 Gate/测试 | 责任人 |
| --- | --- | --- | --- |
| 1 | API / 集成测试 | `backend-java8-test` | 后端 |
| 2 | 单元 / E2E | `frontend-unit`、`compose-playwright-e2e` | 前端 |
| 3 | staging 合同 | `staging-api-contract` | 测试 |

## 环境和测试数据

- 本地：使用 Docker Compose 中的演示账号/匿名数据。
- staging：只允许专用测试账号和可清理数据；需要 `TARGET_ENV=staging`、`ALLOW_MUTATING_E2E=true`。
- 生产：禁止写操作；如需验证，只定义只读检查并由人工审批。

## 模型允许与禁止事项

- 允许：修改业务代码、测试实现、可写进度文件（例如 `docs/work/<任务>.md`）。
- 禁止：修改本文件、`verify/`、`.opencode/`、`e2e/specs/` 和离线校验文件。

## 审核结论

- [ ] 产品确认业务验收条件。
- [ ] 技术确认实现边界与风险。
- [ ] 测试确认每条条件都有可执行验证。
- [ ] 审核后提交到 `docs/tasks/`；从此作为受保护验收合同。
